# Bweeep Forge 1.20.1 login ticket bridge

Build inside WSL with Java 17: `./gradlew verifyIdentityStore build --offline --no-daemon`. The output is `build/libs/bweeep-server-auth-1201-0.2.0.jar`.

Install the same JAR in the Forge 1.20.1 client and the matching Forge 1.20.1 server. The channel is mandatory on both sides. The client reads its one-time ticket from `BWEEP_GAME_TICKET`, which must be a 43-character base64url value supplied by the launcher. The server sends a login query and waits for a response from the client. The server consumes that ticket through `consumeGameTicket` with the Microsoft game name before permitting login. An absent mod, absent ticket, duplicate response, non-200 response, malformed identity, timeout, or network error closes the connection. No authentication bypass flag exists.

The production ticket endpoint is fixed to `https://tmwvrglzjfzauuygofpp.supabase.co/functions/v1/launcher-access`. For an isolated test, the server may set `BWEEP_GAME_TICKET_ENDPOINT=http://127.0.0.1:<port>/...` (or `[::1]`). Any other override fails at startup. Never put a secret or ticket in a command line, manifest, or log. The JAR contains no service-role key.

After a valid ticket is consumed, the server looks up the immutable Supabase account ID in `bweeep-player-identities.json`. Existing mappings remain authoritative and preserve the player's UUID across game-name changes. An unmapped account receives `UUID.nameUUIDFromBytes(UTF-8("BweeepAccount:" + canonicalAccountUuid))`; its current Minecraft UUID, current name, previous names and admin role never select an old character. The profile retains its current name while player data, stats and advancements use the account-bound UUID. Malformed or colliding mappings fail closed. If an unmapped generated UUID already has player data, a backup player file, stats, advancements or an OP entry, login fails pending a reviewed mapping instead of silently adopting it. Keep the identity file with the server world and backups.

For a legacy character migration, the operator must independently verify the immutable account ID and the old character UUID. Reusable current or historical names and a sole OP entry are insufficient ownership evidence. During an agreed maintenance window, stop the server, back up the identity file and world, then add the canonical account UUID as a JSON key with the reviewed character UUID as its string value. For example, `{"11111111-1111-4111-8111-111111111111":"22222222-2222-4222-8222-222222222222"}` binds that one account to that one character. Preserve other mappings, ensure no UUID is assigned to two accounts, and review both characters if the account already has data under another UUID. No automatic file copy, merge or deletion is performed. Existing mappings created by older versions are retained for compatibility and should be checked against independent ownership records; this update cannot establish whether a past automatic adoption was legitimate.

An isolated end-to-end test needs a separate Forge server directory, world, and port. Its mock endpoint should return a successful `consumeGameTicket` result only once for the expected ticket and game name, for example `{"ok":true,"userId":"<UUID>","discordId":"<15-22 digits>","role":"member","previousGameNames":[]}`. Verify three separate connections: no auth JAR is rejected during Forge handshake; auth JAR without a ticket is rejected; auth JAR with a matching ticket is admitted once, then a replay is rejected. Also test that mock HTTP failure rejects. The real production server, world, and port are outside this test.
